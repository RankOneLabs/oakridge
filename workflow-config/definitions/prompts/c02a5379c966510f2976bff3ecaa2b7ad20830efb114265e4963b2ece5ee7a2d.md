# Revise slice assessment

Apply the feedback to the previous assessment and republish. Preserve stable IDs for unchanged items and findings.

Evaluate the slice report under review (`subject`) against the plan and slice build. Check that each criterion and iteration-trigger mark matches its evidence. Check qualifications for every slice case, the paid results against `slice_paid.paid_model_ids`, and the sum of `spend_cents` against `slice_paid.cap_cents`. Check that the generator digest matches the slice build and that the proposed changes are justified.

Publish `slice_assessment` using the development assessment shape with `run_key` copied from the report. Set `head_sha` to the slice build's `build.head_sha`.

- `item_assessments` entries are `{subject: {kind, id}, status, observation, supporting_citations}`. Use kind `criterion`, `trigger`, or `case`, and status `met`, `partial`, or `not_met`. Cover every criterion and trigger exactly once. Criteria are marked `met` or `not_met`; triggers are marked `fired` or `not_fired`. A trigger item’s status records whether its mark is supported by the evidence. Ground judgments in `{kind: file|test|output, citation_location, detail?}` evidence.
- `additional_findings` record other issues with stable IDs, severity (`blocking`, `warning`, or `info`), observations, and evidence.
Use `related_subjects` to tie each additional finding to slice case, criterion, or trigger IDs.

Write each actionable proposal as `{key, instruction, citation?}` with a stable identifier and a concrete correction. When citing evidence, give `{revision_id, pointer}` with an RFC 6901 JSON Pointer. On reassessment, record one `{round_id, outcome}` for each delivered round, including your own update after direct correction, using `verified` or `needs_further_work`. Use empty lists when there are no proposals or verifications.
- Always report `test_evidence` as `{passed, failing_tests, output?, test_notes?, cargo_test_output?}`. Failed tests require an unmet non-trigger item or a blocking or warning finding.
- Set `verdict` to `fail` if any non-trigger item is `partial` or `not_met` or any finding is blocking. Otherwise set it to `pass_with_notes` if any finding is a warning, or `pass` if there are no warnings.

Leave the decision to the operator.

## Long steps

- Publish a provisional artifact as soon as the work supports it, and publish again with the final numbers.
- Run long commands in the foreground with a polling wait (for example a loop that checks a log or status every 30–60 seconds until done). Never leave a command running in the background across turns.
- Before starting any long step, check that this attempt is still running. If it is not, stop.
- Never end your turn before every artifact this step must publish has been published. Ending early fails the attempt.

If the inputs are contradictory, unimplementable or ambiguous in a way only the operator can settle, raise a blocker instead of guessing.
