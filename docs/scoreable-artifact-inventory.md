# Scoreable development artifacts

This inventory covers the producer artifacts declared in `workflow-config/development.yaml`. A scoreable item is a bounded claim or decision that a reviewer can judge against retained evidence. The four rubric checks are: **signal** (a meaningful quality judgment), **bounded** (one item can be judged), **background recoverable** (the evidence needed for judgment is retained), and **extractable** (a stable id or JSON path locates it in one immutable revision). “Repo tier” means the judge must inspect the repository at the recorded commit in addition to the artifact context. “Context” means the run's pinned input, artifacts, reviews, and comments suffice. The verdict describes scoreability, not whether any particular item is good.

| Artifact and item | Signal | Bounded | Background recoverable | Extractable | Judgment background and retained location |
| --- | --- | --- | --- | --- | --- |
| `analysis`: each finding | Yes | Yes | Yes, repo tier | Yes, finding `id` | Original spec in run input; code and behavior in the prepared repository; finding, severity, and source refs in the analysis revision. |
| `analysis`: each requirement status | Yes | Yes | Yes, repo tier | Yes, `/requirements/N/status` | Original spec in run input; requirement description and status in the analysis revision; implementation constraints in the repository. The status has no independent id. |
| `analysis`: each proposed spec update | Yes | Yes | Yes, context; repo tier for code claims | Yes, `/proposed_spec_updates/N` | Original spec in run input, linked `finding_ids` and their evidence in the analysis revision, and approval or request feedback in `review_decision`. |
| `analysis`: each risk | Yes | Yes | Yes, context; repo tier for technical likelihood | Yes, `/risks/N` | Risk and mitigation in the analysis revision, original spec in run input, and repository when the likelihood depends on code. Risks have no id. |
| `spec`: each changed requirement or section | Yes | Yes when addressed by section or text span | Yes, context; repo tier for feasibility | Yes, JSON path or text section within revision | Original spec in run input, approved analysis and its proposed updates, revised spec revision, and spec review decision. `spec` is text, so the consumer must select the span it judges. |
| `tasks`: each task | Yes | Yes | Yes, context; repo tier for implementation scope | Yes, task `id` | Revised spec, approved analysis requirements reached through `requirement_ids`, task description in tasks revision, and tasks review feedback. |
| `plan`: each cohort boundary and dependency | Yes | Yes | Yes, repo tier | Yes, cohort `id` or `/cohorts/N/depends_on` | Revised spec, tasks, repository structure, plan revision, and plan review feedback. |
| `plan`: each cohort decision | Yes | Yes | Yes, context; repo tier for code tradeoffs | Yes, decision `id` within cohort | Cohort scope and decision text in plan revision, tasks and spec upstream, repository for technical tradeoffs. |
| `plan`: each cohort acceptance criterion | Yes | Yes | Yes, context; repo tier for feasibility | Yes, criterion `id` within cohort | Criterion text and `task_ids`/`decision_ids` in plan revision, linked tasks and decisions, spec, and repository where feasibility matters. |
| `plan`: each plan-wide acceptance criterion | Yes | Yes | Yes, context | Yes, `/acceptance_criteria/N` | Spec and full plan revision. These are text and have no downstream item link. |
| `plan`: each risk | Yes | Yes | Yes, context; repo tier for likelihood | Yes, `/risks/N` | Risk and mitigation in plan revision, spec, tasks, and repository for technical claims. |
| `brief`: each decision | Yes | Yes | Yes, context; repo tier for technical rationale | Yes, decision `id` | Plan cohort decision with shared id when present, rationale in brief revision, spec and repository for code tradeoffs. A brief-only decision has no plan item. |
| `brief`: each rejected approach | Yes | Yes | Yes, context; repo tier for technical rationale | Yes, approach `id` | Approach and reason in brief revision, `decision_ids` linking the winning decisions, and repository where the tradeoff is technical. |
| `brief`: each acceptance criterion | Yes | Yes | Yes, context; repo tier for implementation claims | Yes, criterion `id` | Shared plan cohort criterion id and links, self-contained brief text, and the repository for executable claims. |
| `build_result`: each changed-file and test claim | Yes | Yes | Yes, repo tier | Yes, `/changed_files/N`, `/tests`, or `/summary` | Build revision, `head_sha` of the built commit, repository diff and test output. A file list or count alone does not prove behavior. |
| `build_result`: each known issue | Yes | Yes | Yes, context; repo tier for impact | Yes, `/known_issues/N` | Issue and severity in build revision, brief criterion it affects, and repository at `head_sha` for code impact. |
| `assessment`: each finding | Yes | Yes | Yes, repo tier | Yes, `/findings/N` | Brief criterion via `criterion_id` for cohort assessments, typed evidence refs, reviewed build result, repository at assessment `head_sha`, and test output. Integration findings have no brief criterion. |
| `assessment`: verdict and next actions | Yes | Yes, as one overall judgment and individual action | Yes, repo tier | Yes, `/verdict` and `/recommended_next_actions/N` | Findings, test evidence, brief or completed cohorts, repository at `head_sha`, and assessment review feedback. |
| `pr`: PR summary and review status | Limited: routing and completeness only | Yes | Yes, context; repo tier for content claims | Yes, `/summary` and `/review_status` | PR body revision, URL and branch, linked build or integration assessment, and forge state. The URL alone is not a code-quality signal. |

`workspace`, `pr_state`, `observed_state`, and `manual_merge_target` are operational state or copies rather than independent author judgments. They can supply context but are not separate scoring targets. Item ids are scoped to their run task list or cohort; an address also includes run and immutable artifact revision ids. Items without ids use their JSON path in that revision.
