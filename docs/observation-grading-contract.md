# Observation grading contract (L2)

L2 stores independent judgments about an L1 item occurrence. A question is identified by `(question_id, question_version)` within a `(producer, namespace)` pair. An evaluator definition identifies its kind (`model`, `code`, or `human`), backend, provider, model, prompt digest, configuration digest, and runtime revision. Evidence sets pin their references by content or digest and say explicitly when evidence is incomplete.

The five grading tables live in `observation/src/storage/migrations/0003_grading.sql`. The migration runs after the existing revision-links migration. Every subject, question, evidence set, evaluator, execution, and superseded observation reference is constrained within the same producer and namespace. The store offers insertion and reading of grade observations; PostgreSQL also rejects direct updates and deletes. There is no consensus, aggregate, ground-truth, latest, or accepted column.

## Answers and failures

An observation retains the evaluator's answer as `{state:"answered",kind,value}` for `boolean`, `choice`, `ordinal`, `numeric`, `text`, or `structured`. `{state:"abstain"|"unclear",kind,reason}` is explicit and does not stand for a negative answer. Probabilities and confidence accompany the raw answer. A normalized score is null unless the writer supplies a `DecisionPolicy` id and version with it; readers must not infer a default normalization. Human corrections insert a new observation with `supersedes_observation_id`, leaving the first row readable.

This pass has no `DecisionPolicy` registry. Human intake checks that a normalized score has both a policy id and version, but does not verify that the policy exists or that its normalization produced the submitted score. Consumers must treat those stamps as caller-supplied provenance until a separately versioned policy registry and verification path are added.

A failed grader or a repository snapshot question with incomplete evidence creates an `evaluation_execution` with `status:"failed"` and an error, but creates no grade observation. The failed execution is returned by the evaluation request and remains readable through the storage API. The grades read lists only observations.

## HTTP routes

`POST /v1/evaluations` accepts `{identity, context?, runner}`. `runner` is `deterministic` or `stub_model`. `identity` contains `subject_occurrence_id`, `evidence_set_id`, `question_id`, `question_version`, `evaluator_definition_id`, `config_digest`, and `attempt_label`. `context`, when supplied, contains the complete immutable `question`, `evidence`, and `evaluator` definitions and registers them before evaluation. A caller may omit it when those definitions already exist. The deterministic checker compares the question's `input_recipe.expected` with the first evidence reference's `content` using canonical JSON equality and answers a boolean question. The stub model uses a pinned `attempt_controls.answer` and optional `attempt_controls.probabilities` from its evaluator definition. Neither runner needs a credential or network service.

`POST /v1/grades` accepts `{identity, context?, details}` for human intake. `details` contains the typed `answer` and a required `reviewer_id`; it may also carry probabilities, confidence, a named normalization policy and score, reviewer details, comments, rationale, quality flags, and `supersedes_observation_id`. A correction uses a new `attempt_label`. Both POST routes require a tenant-bound token from `OBSERVATION_GRADE_CREDENTIALS`, configured like the existing ingest and read credentials. A replay with the same seven identity fields returns HTTP 200 with the existing execution and observation; a new attempt label creates new rows and returns HTTP 201. Invalid or cross-namespace references return HTTP 422 with no execution or observation.

`GET /v1/items/{occurrence-id}/grades?limit=50&offset=0` uses the existing read credential. URL encode the occurrence ID because a canonical digest contains `/`. The result is `{items,total,limit,offset}`, ordered by recording time and observation id. Each item contains the raw `answer`, full observation including probabilities, evaluator definition and kind, and execution including evidence identity, status, provider link, and external execution id. `limit` ranges from 1 to 200.

The idempotency digest is canonical JSON v1 over the ordered tuple `(subject_occurrence_id, evidence_set_id, question_id, question_version, evaluator_definition_id, config_digest, attempt_label)`. Reusing a label means retrying the same measurement; a deliberate repeat uses a different label. The interfaces in `observation/src/ports/` keep external evaluation backends, artifact producers, and JSONL/Assay experiment exporters outside the service's dependency tree. The local evaluation backend is a no-op mirror; the PostgreSQL grading store is authoritative.
